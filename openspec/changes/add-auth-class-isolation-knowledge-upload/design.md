## Context

当前仓库没有既有业务代码，本变更面向课程项目和可重复验收。实现需要覆盖登录、教师/学生角色、班级隔离、教师上传入库、预置演示数据、Docker Compose 和健康检查，但不需要生产级分布式架构。行为契约见三份 delta spec。

## Goals / Non-Goals

**Goals:**

- 使用小型、易测试的 Flask 服务实现完整的服务端认证、角色授权和班级过滤。
- 使用 SQLite 保存用户、班级、材料与知识库记录，并在 Compose 中持久化。
- 让上传成功、数据库记录、知识库记录和材料列表之间具有清晰的一致性规则。
- 提供预置 A/B 班账号，使跨班拒绝、学生 403 和上传后可查可直接验收。
- `docker compose up` 一键启动；`GET /health` 供探活；密钥与 DB 路径可配置。

**Non-Goals:**

见 `proposal.md` Non-goals（检索问答、对话、作业、SSO、生产 HA 等）

## Decisions

### 1. 使用 Flask、SQLAlchemy 和 SQLite

应用采用 Flask 应用工厂组织配置和扩展，SQLAlchemy 或 Flask-SQLAlchemy 管理模型与事务，pytest 使用 Flask test client 做路由和权限测试。SQLite 数据库文件放在 Flask `instance` 目录或显式数据目录中，容器运行时挂载命名卷。

数据模型至少包含：

- `users`: `id`、唯一 `username`、`password_hash`、`role`、`is_active`。
- `classes`: `id`、唯一 `name`。
- `class_memberships`: `user_id`、`class_id` 唯一组合。
- `sessions`: 会话令牌摘要、`user_id`、到期时间和撤销时间；只保存摘要，不保存原始令牌。
- `materials`: `id`、`class_id`、`uploaded_by`、原始文件名、内部存储名、状态、创建时间。
- `knowledge_documents`: `id`、`material_id` 唯一关联、`class_id`、标题、存储位置和创建时间。

SQLite 启用外键约束，写请求使用短事务。单应用实例、单主机本地命名卷承载数据库目录（包含 SQLite journal/WAL 等附属文件）与上传目录，容器进程对两者具有最小必要读写权限；不将 SQLite 放在网络共享卷上，也不以多实例共享文件方式部署。课程规模下 SQLite 足够，未来扩展到 PostgreSQL 时保持模型和仓储边界不变。

### 2. 使用可撤销的服务端会话与数据库用户加载

登录成功时生成高熵随机会话令牌；Flask 签名 Cookie 只持有令牌（以及 CSRF 所需状态），SQLite `sessions` 表只保存令牌摘要、用户 ID、到期与撤销状态。`SECRET_KEY` 只从环境变量读取，不使用默认值。Cookie 设置 `HttpOnly`、`SameSite=Lax`，HTTPS 环境设置 `Secure`；会话最长有效期为 8 小时，并在服务端校验到期时间。登录时先清除旧 Cookie 状态并创建新令牌，退出时撤销数据库会话且清除 Cookie，因此旧 Cookie 重放也无效。每次请求由服务端会话加载数据库用户、启用状态、角色和班级成员关系，不信任客户端提交的角色或班级。

页面路由未登录时重定向到登录页；JSON API 未登录时返回 401。登录后的 `next` 参数只允许站内安全路径，防止开放重定向。未认证的上传 API 先返回 401；已登录的学生即使没有提交 CSRF 令牌也先返回 403，防止令牌错误掩盖身份/角色拒绝。

选择数据库会话而不是仅靠 Flask 签名 Cookie 或 JWT，是因为仅清除浏览器 Cookie 无法撤销已复制的旧令牌；服务端记录可在退出时立即撤销。Flask 的签名 Cookie 只负责安全传递随机令牌，不作为权限或班级信息的来源。

受保护路由使用统一前置逻辑（装饰器或 `before_request`）：无有效 session → 页面 `302` 至 `/login`；API 返回 `401` JSON。

登录、退出、上传等 Cookie 认证的非安全方法统一验证 CSRF 令牌。登录页面先发放令牌并在提交凭据前验证；上传与退出等受保护写路由按“认证 → 角色（上传）→ CSRF → 班级/业务”顺序执行，可使用 Flask-WTF 生成和校验令牌，但不能让全局预检查掩盖未认证 401 或学生上传 403。HTML 表单使用隐藏字段，脚本请求使用约定请求头；CSRF 失败返回 400/403 且无副作用。`SameSite=Lax` 不能替代 CSRF 校验，`GET /health` 等只读路由不要求令牌。

### 3. 使用专用密码哈希函数

账号初始化和后续密码变更统一调用密码服务。优先使用 Werkzeug `generate_password_hash(..., method="scrypt")` 与 `check_password_hash`；若项目依赖已包含 Argon2，也可使用 Argon2id，但不得使用 SHA-256 等通用快速哈希直接存密码。

初始化密码通过 `SEED_TEACHER_PASSWORD`、`SEED_STUDENT_PASSWORD` 等服务端环境变量传入，只在内存中参与哈希，不写入日志、命令行参数或 Compose 文件。用户表只保存 `password_hash`。

### 4. 预置数据通过幂等 Flask CLI 命令创建

提供类似 `flask seed-demo` 的命令，使用稳定用户名或自然键幂等创建：A 班、B 班、A 班教师、A 班学生和 B 班学生及成员关系。重复执行时更新缺失关系但不生成重复记录。命令输出只显示创建/已存在状态，不回显密码。

预置数据既用于课堂演示，也作为跨班测试夹具：A 班账号访问 B 班材料必须得到 403；学生直接调用上传接口必须得到 403。

### 5. 班级过滤在服务端查询层强制执行

认证装饰器负责加载当前用户；教师装饰器只负责角色判断；班级授权函数根据 `class_memberships` 判断目标 `class_id` 是否允许。采用 `/classes/<class_id>/materials`、`/classes/<class_id>/materials/<material_id>` 及其上传、下载子路由：`class_id` 是用户选择的目标，不是授权依据；每次都用数据库成员关系校验，教师属于多个班时也可明确选择其中一个。材料列表、详情、下载和上传均先校验班级，跨班返回统一的 403；目标班级已授权但材料不存在返回 404。

查询材料时同时使用资源条件和班级条件，例如按 `material_id` 查询时仍附加允许的 `class_id`。不能先取出任意材料再依赖前端隐藏，也不能使用请求中的 `user_id` 或 `role`。学生可读取本班 `ready` 材料，但任何上传请求在保存文件之前返回 403。

新记录的 `class_id` 只取自**已校验的 URL 目标班级**，拒绝与 URL 不一致的表单班级字段；不得从 Cookie/表单中的自称班级直接取值。学生 A 班列表不可看到 B 班标题，A 班教师以 B 班 URL 或材料 ID 访问必须被服务端拒绝。下载只按数据库保存的内部文件名从非公开目录读取；授权后返回 `Content-Disposition: attachment` 与 `X-Content-Type-Options: nosniff`，不提供内联预览或 Markdown HTML 渲染。

### 6. 上传采用“先授权、再校验、后事务入库”的数据流

上传流程如下：

1. 验证会话、教师角色和目标班级成员关系。
2. 在读入文件前设置请求体上限（例如 11 MiB，允许 multipart 开销），流式计数单文件最多 10 MiB，超限统一返回 413。允许 `.pdf`、`.txt`、`.md`（大小写不敏感）；扩展名只是第一道检查，客户端 MIME 不可信。PDF 须具备正确签名并通过带安全资源限制的 PDF 解析器验证基本结构；TXT/MD 须能严格解码为 UTF-8（可接受 UTF-8 BOM），非空且拒绝 NUL、明显二进制签名与异常控制字符；拒绝 DOCX、PPTX、ZIP 等其他类型。
3. 限制原始文件名长度，仅保留用于展示的安全名称；由服务端生成随机内部文件名。将文件暂存于非公开、仅应用可写的目录，验证后写入最终目录；不得使用用户提供的路径或对上传内容进行内联渲染。
4. 在同一 SQLite 事务中创建 `materials` 和 `knowledge_documents`，两条记录使用已校验的相同 `class_id`，材料状态设为 `ready`；只有提交成功才返回成功，列表只查询当前用户班级的 `ready` 记录。
5. 若数据库写入失败，回滚事务并清理本次文件；进程异常中断可能留下孤儿文件，提供按存储引用对账的清理命令，仅清理超过安全等待期且未被数据库引用的文件。磁盘写入失败不得创建 `ready` 记录。

本课中的“写入知识库”定义为创建可被后续知识能力使用的 `knowledge_documents` 元数据记录并关联原始文件；不在本次实现内容提取、文本切块、向量化或检索问答。即使 Markdown 可解码，也只作为附件保存，不执行其中的 HTML 或脚本。该边界与 proposal 的 Non-Goals 一致。

### 7. Compose 持久化 SQLite 与上传目录

Dockerfile 以非 root 用户运行 Flask 应用，Compose 负责构建应用、传入环境变量、暴露 HTTP 端口，并将 SQLite 数据库及上传目录放在同一主机的本地命名卷中。镜像不包含真实密钥或演示密码；仓库只提交 `.env.example` 的变量名，真实值由运行者提供，`.env` 不进入版本控制。

课程基线只有一个应用实例（含服务端会话），因为 SQLite 与知识库记录都在应用数据卷中；容器不得多实例共享数据库文件。容器启动命令先完成数据库建表或迁移，再启动 Web 服务；初始化演示数据通过显式命令执行，避免每次启动覆盖已有账号。

### 8. GET /health 同时用于人工和 Compose 探活

`GET /health` 不受登录保护。端点检查：必需配置已加载、SQLite 可执行 `SELECT 1`、上传目录存在且可写。全部通过时返回 `200 {"status":"ok"}`；任一关键检查失败时返回 503 和简化组件状态，不返回数据库绝对路径、密钥或异常堆栈。

Compose healthcheck 使用容器内 HTTP 请求访问该端点，并配置合理的启动等待、间隔和重试次数。

## Risks / Trade-offs

- [SQLite 并发写能力有限且共享卷锁不可靠] → 本课使用短事务、单实例和本地主机卷；生产 HA 明确不在范围内。
- [Cookie 被窃取会导致会话冒用] → 设置 `HttpOnly`、`SameSite`、HTTPS `Secure` 和 8 小时过期；服务端只保存摘要，退出时撤销会话并避免记录 Cookie。
- [跨站请求借助已登录 Cookie 写入数据] → 对登录、退出、上传等写路由验证 CSRF 令牌，并覆盖缺失和伪造令牌的测试。
- [遗漏查询中的班级条件会造成越权] → 把班级检查封装为复用函数，并对列表、详情、下载和上传逐一路由编写跨班测试。
- [文件已保存但进程在事务提交前崩溃会产生孤儿文件] → 捕获常规异常时清理，提供安全等待期后的对账清理命令并测试故障分支。
- [PDF 可包含危险内容、Markdown 可包含 HTML] → 不内联预览，下载强制附件和 `nosniff`；本期不承诺恶意软件扫描。
- [预置密码可能被当作生产密码] → 密码只从环境变量传入，文档明确预置数据仅用于课程演示。

## Migration Plan

1. 创建 Flask 应用工厂、配置、数据库和测试骨架。
2. 创建 SQLite 模型、建表/迁移与幂等 `seed-demo` 命令。
3. 实现登录、退出、会话保护和角色检查。
4. 实现班级过滤、材料列表和跨班拒绝。
5. 实现教师上传、知识库记录事务与失败清理。
6. 添加 Dockerfile、Compose、持久化卷和 `GET /health`。
7. 在 Compose 环境执行完整测试和规格严格校验；回滚时停止新容器并保留数据卷。
